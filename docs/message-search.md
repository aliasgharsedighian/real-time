# جست‌وجوی پیام‌های یک گفتگو

جست‌وجوی کنار آیکون تماس برای همان گفتگوی باز، چه دونفره و چه گروهی، فعال است. پنل نتیجه نام/آواتار فرستنده، زمان و بخشی از متن اطراف عبارت را نشان می‌دهد. در دسکتاپ پنل کنار گفتگو و در موبایل روی گفتگو باز می‌شود؛ انتخاب نتیجه در موبایل پنل را می‌بندد. بستن پنل یا Escape خود گفتگو را نمی‌بندد.

جست‌وجو فقط در `Message.content` پیام‌های `kind=TEXT` و در سرور انجام می‌شود؛ نام فایل، نام کاربر و رویدادهای سیستمی نتیجهٔ جست‌وجوی پیام نیستند. متن همراه ضمیمه چون در content است قابل جست‌وجو است. متن فارسی پشتیبانی می‌شود؛ تفاوت حروف فارسی/عربی و اعراب نرمال‌سازی نمی‌شود. برای محدودکردن جست‌وجوهای بدون trigram، عبارت باید حداقل سه حرف یا رقم متوالی داشته باشد؛ حداکثر طول ۱۰۰ کاراکتر است.

## API و دسترسی

هر دو مسیر JWT و عضویت فعلی همان گفتگو را بررسی می‌کنند؛ خروج یا حذف از گروه دسترسی را قطع می‌کند. دریافت نتایج/تاریخچه در REST رسید خواندن نمی‌نویسد.

- `GET /api/v1/realtime/polling/:id/search?q=...&beforeId=...`: حداکثر ۲۰ نتیجه، جدید به قدیم با ترتیب پایدار id و `nextCursor`. دریافت ۲۱ رکورد برای تشخیص صفحهٔ بعد، جای COUNT کامل را می‌گیرد. هر نتیجه حداکثر ۳۲۰ کاراکتر از حوالی عبارت و اطلاعات فرستنده دارد. `%`، `_` و backslash literal هستند و SQL پارامتری است. نرخ مستقل جست‌وجو ۶۰ درخواست در دقیقه برای هر کلید پیش‌فرض Throttler است. سقف زمان SQL برابر ۲٫۵ ثانیه است.
- `GET /api/v1/realtime/polling/:id/window?aroundId=...`: تا ۵۰ پیام اطراف نتیجه، شامل خود پیام، با `beforeId` و `afterId` برای ادامهٔ پیمایش. پیام مقصد باید متعلق به همان گفتگو باشد.
- همین مسیر window با دقیقاً یکی از `beforeId` یا `afterId` تا ۵۰ پیام در جهت انتخابی می‌گیرد. cursor نامعتبر یا متعلق به گفتگوی دیگر پذیرفته نمی‌شود.

پاسخ‌ها envelope معمول `{statusCode,message,data}` دارند. نتایج جست‌وجو مستقل از cache تاریخچه‌اند. انتخاب پیام بارگذاری‌نشده، cache را با بازهٔ متصل اطراف آن جایگزین می‌کند؛ پیام‌های آخر گفتگو به این بازهٔ جدا چسبانده نمی‌شوند. پیام مقصد بدون کادر یا پس‌زمینهٔ اضافه در محدودهٔ دید قرار می‌گیرد؛ نتیجهٔ انتخاب‌شده فقط در فهرست نتایج مشخص می‌شود. دکمه‌های دریافت قدیمی‌تر/جدیدتر و بازگشت به آخر گفتگو در حالت تاریخچه فعال‌اند. پیام زنده‌ای که بیرون از بازه است به آن اضافه یا خوانده‌شده اعلام نمی‌شود. جست‌وجو با تأخیر ۳۵۰ میلی‌ثانیه و لغو درخواست منسوخ انجام می‌شود؛ خطای بازکردن نتیجه پیام‌های فعلی را حذف نمی‌کند.

## دیتابیس و استقرار

migration `20261104140000_message_search` افزونهٔ `pg_trgm`، ایندکس B-tree روی `(chatId,id)` و ایندکس partial GIN روی content برای `kind=TEXT` می‌سازد. GIN از جست‌وجوی substring با ILIKE پشتیبانی می‌کند؛ [مرجع PostgreSQL](https://www.postgresql.org/docs/17/pgtrgm.html). ایندکس partial در SQL migration نگهداری می‌شود چون schema فعلی Prisma آن را بیان نمی‌کند؛ در migrationهای بعدی حفظ شود.

```bash
cd backend
npx prisma migrate deploy
npm run build
npm run test:search:integration
```

روی محیط مقصد پیش از استفاده از قابلیت، migration اجرا و سرویس بک‌اند به‌روزرسانی شود. حساب migration باید امکان نصب pg_trgm داشته باشد. ساخت ایندکس معمولی روی جدول بزرگ می‌تواند موقتاً نوشتن را منتظر نگه دارد؛ استقرار روی دیتابیس بزرگ نیاز به زمان‌بندی مناسب یا برنامهٔ ساخت concurrent ایندکس دارد. هیچ migration قبلی بازنویسی و هیچ پیام موجود حذف نمی‌شود.

تست integration از کاربران/گفتگوهای fixture با پاک‌سازی همان شناسه‌ها استفاده می‌کند؛ دیتابیس تست تنظیم شود. پوشش شامل مجوزها، چت دونفره/گروهی، فارسی، ورودی literal/SQL، cursor، بازهٔ پیام بدون شکاف، بدون تغییر رسید خواندن و EXPLAIN برای ایندکس GIN است. fixture بزرگ‌تر نیز ۶٬۰۰۰ پیام اضافه می‌کند تا پیدا شدن نتیجه خارج از صفحهٔ اخیر بررسی شود. این تست benchmark بار هم‌زمان یا تضمین زمان پاسخ در دیتابیس production نیست.
