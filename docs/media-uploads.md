# آپلود عکس و ویدئو

ماژول مشترک `backend/src/modules/files-upload/` از الگوی FileUploadModule، سرویس آپلود و سرویس بهینه‌سازی پروژهٔ `nest-nodejs-webinar` اقتباس شده است. مسیرها و کد مخصوص محصول/مقاله با سرویس قابل استفاده برای آواتار و چت جایگزین شده‌اند. نام فایل ورودی هرگز برای مسیر دیسک استفاده نمی‌شود.

## محدودیت‌ها و خروجی

مرجع محدودیت‌ها `upload.policy.ts` و API احراز هویت‌شدهٔ `GET /api/v1/files/policy` است؛ فرانت محدودیت نوع و حجم را از همین API می‌گیرد. اعتبارسنجی واقعی فایل و ابعاد/مدت در سرور انجام می‌شود.

| کاربرد | ورودی | حداکثر | خروجی |
| --- | --- | --- | --- |
| عکس پروفایل | JPEG، PNG، WebP غیرمتحرک | ۵ MiB، ۴۰ مگاپیکسل | WebP کیفیت ۸۰، برش تا ۵۱۲×۵۱۲ |
| عکس چت | JPEG، PNG، WebP غیرمتحرک | ۱۰ MiB، ۴۰ مگاپیکسل | WebP کیفیت ۸۰، ضلع بزرگ حداکثر ۱۹۲۰ |
| ویدئوی چت | MP4، WebM، MOV با هدر ftyp/EBML | ۱۰۰ MiB، ۵ دقیقه، حداکثر مساحت 4K | MP4 با H.264/AAC، ضلع بزرگ حداکثر ۱۲۸۰، حداکثر ۳۰fps |

تصاویر با Sharp چرخش EXIF را اعمال می‌کنند و بدون metadata ذخیره می‌شوند. فایل اصلی پس از پردازش حذف می‌شود. ویدئو با FFprobe بررسی و با FFmpeg بازکدگذاری می‌شود؛ این کار بر عهدهٔ Sharp نیست. کاهش حجم برای هر فایل از پیش فشرده‌شده تضمین نمی‌شود. خروجی ویدئو به سقف ۱۰۰ MiB محدود است؛ خروجی ناقص پذیرفته نمی‌شود. همزمان حداکثر دو فایل در هر پردازه پردازش می‌شود و درخواست اضافه 503 قابل تلاش مجدد می‌گیرد. زمان پردازش تصویر ۳۰ ثانیه و ویدئو ۱۸۰ ثانیه محدود شده است.

## API و چرخهٔ فایل

تمام مسیرهای زیر JWT Bearer می‌خواهند. هر درخواست multipart فقط یک فیلد فایل به نام `file` می‌پذیرد. پیام می‌تواند یک عکس، ویدئو یا ویس داشته باشد، یا حداکثر ۱۰ عکس را در یک آلبوم نگه دارد.

- `POST /api/v1/files/avatar`: پردازش و اتصال اتمیک به پروفایل کاربر فعلی؛ پاسخ Profile شامل `avatarId`. تعویض همزمان سری می‌شود و فایل آواتار قبلی پاک می‌شود.
- `DELETE /api/v1/files/avatar`: حذف آواتار فعلی؛ پاسخ Profile.
- `POST /api/v1/files/chats/:chatId`: فقط برای عضو گفتگو؛ پاسخ `{ id, kind, mimeType, size, width, height, duration? }`. ابتدا فایل پیش‌نویس است.
- `DELETE /api/v1/files/:id`: فقط مالک فایل پیش‌نویس چت؛ فایل ارسال‌شده حذف نمی‌شود.
- `GET /api/v1/files/:id/content`: آواتارها برای کاربران واردشده، ضمیمه‌های ارسال‌شده فقط برای اعضای همان چت، پیش‌نویس فقط برای مالک عضو چت. پاسخ private/no-store و دارای پشتیبانی Range است. مسیر دیسک یا URL دارای توکن به کلاینت داده نمی‌شود.

رویداد `message:send` این ورودی را می‌پذیرد:

```json
{ "chatId": 1, "content": "کپشن اختیاری", "attachmentId": "UUID returned by upload" }
```

برای آلبوم، به‌جای `attachmentId` آرایهٔ مرتب `attachmentIds` ارسال می‌شود. سرور شناسه‌های تکراری، ضمیمهٔ نامعتبر و آلبوم غیرعکس را رد می‌کند. همهٔ فایل‌ها در تراکنش ساخت پیام وصل می‌شوند و با همان ترتیب در تاریخچه و فوروارد نمایش داده می‌شوند.

هویت فرستنده فقط از JWT سوکت می‌آید؛ `senderId` و `userId` ارسالی مبنای دسترسی نیستند. فایل با شرط مالکیت، chatId، انقضانداشتن و استفاده‌نشدن داخل تراکنش به پیام متصل می‌شود. تلاش دوباره با همان attachmentId پیام تکراری نمی‌سازد. پیام متنی بدون ضمیمه همچنان مجاز است؛ متن خالی فقط همراه ضمیمه پذیرفته می‌شود و متن تا ۱۰۰۰۰ کاراکتر محدود است. REST ارسال پیام نیز همین منطق را دارد. تاریخچه، پیام زنده و آخرین پیام فهرست چت شامل `attachments` هستند.

پیش‌نویس‌ها پس از ۲۴ ساعت منقضی می‌شوند. پاک‌سازی هنگام آغاز برنامه و هر ساعت فایل‌های استفاده‌نشده، ورودی‌های موقت و خروجی‌های بدون رکورد قدیمی را جمع‌آوری می‌کند. خطای اعتبارسنجی/پردازش/دیتابیس فایل ورودی و خروجی ناقص را پاک می‌کند.

فرانت در `frontend/` انتخاب و پیش‌نمایش، درصد واقعی انتقال، وضعیت پردازش، لغو آپلود چت، ارسال با/بدون کپشن، پخش و دانلود را دارد. فایل‌ها با درخواست احراز هویت‌شده به Blob دریافت می‌شوند و URL محلی هنگام خروج از کامپوننت آزاد می‌شود. در این نسخه ویدئو برای پخش کامل دریافت می‌شود؛ پخش شبکه‌ای تکه‌ای در UI پیاده نشده، هرچند API از Range پشتیبانی می‌کند. فایل منتخب در همان صفحه هنگام خطا باقی می‌ماند؛ فایل محلی با reload بازیابی نمی‌شود. پس از شکست تأیید ارسال، شناسهٔ فایل حفظ می‌شود تا retry دوباره آپلود نکند. draft متن مطابق قبل ذخیره می‌شود.

انتخاب یک یا چند عکس پیش‌نمایش با گزینه‌های افزودن، حذف، کپشن و گروه‌بندی باز می‌کند. در حالت تکی، کپشن و Reply به اولین پیام موفق تعلق دارند. اگر ارسال تکی قطع شود، پیش‌نمایش فقط عکس‌های باقی‌مانده را نگه می‌دارد. هنگام آپلود، پیشرفت و دکمهٔ لغو روی پیش‌نمایش پیام دیده می‌شوند. عکس تکی با نسبت اصلی و آلبوم در یک شبکه نمایش داده می‌شوند. هر عکس در گالری با دانلود و در آلبوم با حرکت قبلی/بعدی باز می‌شود.

## اجرا و استقرار

```bash
cd backend
npm install
npx prisma generate
npx prisma migrate deploy
npm run build
npm run start:dev
```

Migration `20261103100000_media_uploads` روی دیتابیس محلی `test_realtime` اعمال شده است. در محیط‌های دیگر باید migration اجرا شود. تغییرهای افزایشی آن جدول UploadFile و فیلد اختیاری avatarId هستند. برای آلبوم، migration `20261106110000_album_attachment_order` موقعیت هر ضمیمه را اضافه می‌کند. پیام‌های قدیمی نیازی به تبدیل ندارند.

`UPLOAD_DIR` اختیاری است و پیش‌فرض آن `uploads` نسبت به working directory بک‌اند است. برای نمونه روی سرور مقصد آن را به `/data/batgram/uploads` تنظیم کنید و همین پوشه را به volume ماندگار وصل کنید. مسیر نسبی هر فایل در دیتابیس ذخیره می‌شود؛ برای جابه‌جایی ذخیره‌سازی کل پوشه را منتقل و همین متغیر را عوض کنید. برای رفتن به object storage پیاده‌سازی سرویس باید تغییر کند. پوشهٔ آپلود عمومی/static نشود؛ مسیر API مجوز را بررسی می‌کند. هنگام backup دیتابیس، پوشهٔ رسانه هم نگهداری شود.

FFmpeg و FFprobe با وابستگی‌های npm نصب می‌شوند. نصب باید دانلود باینری پلتفرم را مجاز کند. برای باینری سفارشی `FFMPEG_PATH` و `FFPROBE_PATH` قابل تنظیم‌اند. در چند نمونهٔ بک‌اند باید storage مشترک باشد؛ سقف همزمانی برای هر نمونه مستقل است. در این نسخه صف پردازش جداگانه وجود ندارد.

در reverse proxy برای multipart سربار در نظر بگیرید؛ مثلاً `client_max_body_size 105m` و `proxy_read_timeout 240s`. تنظیمات production با این تغییر به‌صورت خودکار ویرایش نشده‌اند. پس از نصب وابستگی‌ها و migration، پردازهٔ فعال بک‌اند را با روش معمول پروژه restart کنید.

## بررسی

```bash
cd backend
npm test -- --runInBand
npm run test:media:integration
cd ../frontend
npm run build
npm run lint
npm test
```

آزمون یکپارچه به دیتابیس محلی تنظیم‌شده نیاز دارد. سه حساب و یک چت موقت می‌سازد، انتقال عکس و ویدئوی واقعی، دسترسی عضو/غیرعضو، هویت سوکت، جلوگیری از اتصال دوباره، تاریخچه، تعویض آواتار و Range را بررسی و داده‌ها/فایل‌های خودش را حذف می‌کند. برای محیط production اجرا نشود. تست‌های واحد HTTP فایل جعلی، حجم بیش از حد، چندفایلی، فایل موقت و مالکیت را پوشش می‌دهند. تست‌های فرانت ارسال بدون کپشن، حفظ فایل بعد از خطا و retry با همان شناسه را بررسی می‌کنند.

مراجع: [آپلود NestJS](https://docs.nestjs.com/techniques/file-upload)، [خروجی Sharp](https://sharp.pixelplumbing.com/api-output/)، [FFmpeg](https://ffmpeg.org/ffmpeg.html).

## پیام صوتی

دکمهٔ مشترک میکروفون/ارسال در فرانت فعال با متن یا ضمیمه به ارسال تغییر می‌کند. نگه‌داشتن با ماوس، لمس یا Space/Enter ضبط را شروع و رهاکردن پیش‌نمایش محلی پخش‌شونده را آماده می‌کند؛ آپلود فقط پس از تأیید ارسال انجام می‌شود. لغو، خروج از چت و مخفی‌شدن صفحه میکروفون را آزاد می‌کنند. اگر مجوز پس از رهاکردن برسد، ضبط شروع نمی‌شود و کاربر باید دوباره نگه دارد. ضبط به HTTPS یا localhost، مجوز میکروفون و MediaRecorder نیاز دارد.

سیاست API شامل audioMaxBytes (۲۰ MiB)، audioMaxSeconds (۳۰۰) و audioMimeTypes است. ضبط تا پنج دقیقه محدود می‌شود. ورودی WebM، MP4/M4A، Ogg، MP3 و WAV پذیرفته می‌شود؛ سرور کانتینر و جریان واقعی صوت را بررسی و با FFmpeg به AAC تک‌کاناله در M4A (`audio/mp4`) تبدیل می‌کند. فایل دارای `kind: AUDIO`، مدت واقعی و width/height صفر است؛ با schema فعلی سازگار است و migration جدید لازم ندارد. کنترل دسترسی، فایل پیش‌نویس، retry ارسال و پاک‌سازی مانند سایر رسانه‌هاست. پیام و پیش‌نمایش با audio controls پخش می‌شوند؛ فهرست گفتگو «Voice message» نشان می‌دهد.

انتخابگر `emoji-picker-react` هنگام بازشدن به‌صورت lazy بارگذاری می‌شود و ایموجی Unicode را در محل مکان‌نما درج می‌کند؛ تم روشن/تاریک برنامه را دنبال می‌کند.

عکس گروه با همان محدودیت و پردازش عکس پروفایل پشتیبانی می‌شود؛ تغییر/حذف فقط توسط مالک و مشاهده فقط برای اعضای فعلی مجاز است. مسیرهای `files/groups/:chatId/avatar` و چرخهٔ ذخیره‌سازی در [قرارداد گروه‌ها](group-chats.md#group-photos-and-member-discovery) ثبت شده‌اند.
