# تماس صوتی و تصویری دونفره

تماس روی فرانت اصلی `frontend/` پیاده شده است. در سربرگ گفتگوی دونفره، دکمهٔ تلفن دو گزینهٔ Voice call و Video call دارد؛ تماس تصویری همزمان صدا را هم منتقل می‌کند. Calls در سایدبار به `/dashboard/calls` و صفحهٔ تماس به `/dashboard/calls/active` می‌رود. همهٔ این مسیرها زیر همان اعتبارسنجی نشست `/dashboard` هستند. گروه‌ها در UI دکمهٔ تماس ندارند و سرور نیز درخواست تماس گروهی را رد می‌کند.

## رفتار

- شروع تماس پس از دریافت مجوز و آماده‌شدن رسانه انجام می‌شود؛ خطای مجوز به مخاطب زنگ نمی‌زند. پذیرش نیز تا آماده‌شدن رسانه مهلت زنگ را متوقف نمی‌کند.
- سرور از زمان شروع، ۳۰ ثانیه برای پاسخ فرصت می‌دهد. بی‌پاسخ `MISSED`، ردشده `REJECTED`، لغوشده `CANCELLED` و خطای ارتباط `FAILED` ثبت می‌شود. پس از پذیرش، اتصال رسانه نیز حداکثر ۳۰ ثانیه فرصت دارد.
- فقط بعد از تأیید اتصال رسانه از هر دو طرف، تماس `ACTIVE` و زمان مکالمه ثبت می‌شود. قطع تماس فعال `ENDED` است.
- اعلان تماس ورودی در همهٔ صفحه‌های داشبورد نمایش داده می‌شود و صدا دارد. پخش خودکار زنگ ممکن است طبق سیاست مرورگر مسدود شود؛ اعلان دیداری و پذیرش همچنان کار می‌کنند. سوکت دوباره‌متصل‌شده دعوتی را که هنوز در مهلت است بازیابی می‌کند.
- در هر لحظه هر کاربر فقط یک تماس دارد. تماس همزمان و معکوس کنترل می‌شود. اگر چند تب باز باشند، پذیرش فقط یک دستگاه را به تماس متصل می‌کند؛ سیگنال‌ها به همان دو سوکت می‌روند.
- کنترل قطع میکروفون، خاموش‌کردن تصویر، پایان تماس و بازگشت به صفحهٔ تماس هنگام جابه‌جایی بین صفحه‌ها وجود دارد. پایان تماس، خروج از حساب، timeout و قطع سوکت، trackها و peer connection را آزاد می‌کنند. قطع موقت مسیر رسانه ۱۰ ثانیه فرصت بازیابی دارد.
- طرف دریافت‌کننده برای زنگ خوردن باید داشبورد را باز و سوکت متصل داشته باشد. تماس در پس‌زمینهٔ بسته‌شدهٔ PWA یا push notification پیاده نشده است.
- سابقهٔ ۱۰۰ تماس آخر از PostgreSQL می‌آید؛ رسانه، SDP و ICE ذخیره نمی‌شوند. راه‌اندازی مجدد بک‌اند، تماس‌های ناتمام قبلی را `FAILED` می‌کند.

## اجرا و استقرار

ابتدا migration را اعمال و بعد بک‌اند را با Prisma Client جدید اجرا کنید:

```bash
cd backend
npx prisma generate
npx prisma migrate deploy
npm run build
```

دسترسی دوربین و میکروفون به HTTPS یا localhost نیاز دارد. فرانت و سوکت production نیز باید HTTPS/WSS باشند. سیگنال‌دهی همان namespace احراز هویت‌شدهٔ `/chat` است؛ فایل‌ها یا صدا از Socket.IO منتقل نمی‌شوند.

STUN پیش‌فرض `stun:stun.l.google.com:19302` است. برای اتصال بین شبکه‌های محدود، اینترنت موبایل و NATهای مختلف، TURN واقعی لازم است. در محیط بک‌اند برای coturn با `use-auth-secret` تنظیم کنید:

```dotenv
WEBRTC_TURN_URLS=turn:turn.example.com:3478?transport=udp,turns:turn.example.com:5349?transport=tcp
WEBRTC_TURN_SECRET=<coturn-static-auth-secret>
```

مقادیر بالا نمونه‌اند. سرور TURN و DNS/TLS آن باید جداگانه راه‌اندازی شوند؛ سرویس TURN با این تغییر نصب یا provision نشده است. secret فقط در بک‌اند می‌ماند؛ `call:config` اعتبارنامهٔ HMAC-SHA1 با اعتبار ۲۴ ساعت به کاربر احراز هویت‌شده می‌دهد. متغیرهای `VITE_*` محل secret نیستند.

هماهنگ‌کنندهٔ تماس فعلی در حافظهٔ یک پردازش بک‌اند است. برای چند replica یا چند worker باید هماهنگی مشترک، رزرو کاربر و timerها به Redis/سرویس مشترک منتقل شوند؛ Socket.IO adapter به‌تنهایی کافی نیست. در استقرار فعلی یک instance برای تماس‌ها اجرا شود.

## قرارداد سوکت

همهٔ رویدادها از JWT هویت می‌گیرند و ack خطا `{ message }` دارد:

| رویداد | درخواست / نتیجه |
| --- | --- |
| `call:start` | `{ chatId, mode: "audio" \| "video" }` → رکورد تماس |
| `call:accept` | `{ id }` → رکورد؛ فقط مخاطب و فقط در مهلت |
| `call:end` | `{ id, failed? }` → پایان؛ فقط طرفین مجاز |
| `call:connected` | `{ id }` → اعلام اتصال رسانهٔ هر طرف |
| `call:signal` | `{ id, signal }`؛ offer از تماس‌گیرنده، answer از مخاطب، ICE از هر دو |
| `call:list` | ۱۰۰ رکورد آخر همان کاربر |
| `call:pending` | دعوت در حال زنگ همان کاربر یا null |
| `call:config` | `{ iceServers }` شامل STUN و TURN تنظیم‌شده |
| `call:updated` | تغییر وضعیت برای همهٔ دستگاه‌های طرفین |
| `call:accepted` | آماده‌سازی offer/answer فقط روی دو دستگاه انتخاب‌شده |

حجم سیگنال حداکثر ۶۴ KiB است؛ سوکت شخص ثالث یا تب انتخاب‌نشده اجازهٔ تزریق سیگنال ندارد. ICE تا رسیدن remote description صف می‌شود و offer/answer به‌ترتیب پردازش می‌شوند.

## بررسی

```bash
cd frontend
npm run build
npm run lint
npm test

cd ../backend
npm run build
npm test -- --runInBand calls.service.spec.ts
npm run test:calls:integration
```

تست‌های واحد سرور مهلت دقیق ۳۰ ثانیه، مشغولی همزمان، محدودیت عضویت و گروه، نقش و دستگاه سیگنال‌دهنده و آزادسازی تماس را پوشش می‌دهند. تست‌های فرانت مجوز، صوت بدون تصویر، ویدئو همراه صوت، کنترل trackها، لغو حین مجوز و آزادسازی منابع را می‌سنجند. تست یکپارچه با کاربران موقت، PostgreSQL و Socket.IO واقعی اجرا و داده‌های خودش را پاک می‌کند؛ شامل انتظار واقعی ۳۰ ثانیه است. این تست‌ها تأیید انتقال رسانه میان دو دستگاه یا عملکرد TURN در شبکهٔ مقصد نیستند؛ آن بررسی هنوز لازم است.

مراجع پیاده‌سازی: [WebRTC signaling در MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling)، [اتصال و TURN در WebRTC](https://webrtc.org/getting-started/peer-connections).

نتیجهٔ بررسی در ۲۰۲۶-۱۱-۰۴: build فرانت و بک‌اند، lint فرانت و فایل‌های اجرایی تغییرکردهٔ بک‌اند، ۵۱ تست فرانت، ۸ تست واحد تماس، ۴ تست یکپارچهٔ تماس و ۳ تست PWA موفق بودند. migration روی دیتابیس توسعهٔ محلی اعمال شد. دانلود Chromium آزمایشی به timeout خورد؛ انتقال رسانه و ظاهر صفحه در مرورگر واقعی در این بررسی تأیید نشده‌اند.
