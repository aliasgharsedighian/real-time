# اعلان پیام‌های BatGram

نسخهٔ فعال فرانت `frontend/` است. اعلان‌ها برای ارسال از سوکت و REST، در چت دونفره و گروهی از مسیر مشترک `ChatGateway.broadcast` پس از ثبت پیام فعال می‌شوند. فعالیت‌های سیستمی گروه و پیام خود کاربر اعلان ندارند.

## رفتار

| وضعیت دریافت‌کننده | نتیجه |
| --- | --- |
| هیچ پنجرهٔ فعال از اپ ندارد، یا تب/پنجره در پس‌زمینه است | Push مرورگر با Firebase Cloud Messaging، در صورت فعال‌بودن و اجازهٔ کاربر |
| اپ در حال مشاهده است و گفتگوی دیگری/پروفایل باز است | کارت اعلان داخلی با توکن‌های رنگی تم جاری |
| همان گفتگو در یکی از تب‌های فعال باز است | بدون اعلان داخلی و مرورگر |

«فعال» یعنی تب visible و دارای focus. اتصال سوکت به‌تنهایی نشانهٔ مشاهدهٔ اپ نیست. حضور هنگام focus/blur، visibilitychange، جابه‌جایی صفحه و join اتاق به‌روز می‌شود؛ heartbeat هر ۲۰ ثانیه و انقضا پس از ۶۰ ثانیه است. قطع سوکت و انقضای JWT حضور را حذف می‌کنند. سیاست در سطح حساب است: دیدن همان چت در یک دستگاه، ارسال Push به بقیهٔ دستگاه‌ها را نیز متوقف می‌کند. هماهنگ‌کنندهٔ فعلی، مانند تماس‌ها، یک پردازش بکند را فرض می‌کند؛ قبل از اجرای چند replica باید حضور و fan-out در adapter/store مشترک قرار گیرند.

کارت داخلی حداکثر سه گفتگو را نشان می‌دهد، پیام‌های یک گفتگو را با شمارنده جمع می‌کند، بعد از هشت ثانیه بسته می‌شود و دکمهٔ بستن و بازکردن گفتگو دارد. نمایش متن با `dir=auto` برای فارسی/انگلیسی است. رنگ‌ها از `brand`، `card`، `primary` و سایر توکن‌های فعلی در هر دو تم می‌آیند. تنظیمات در **Profile → Notifications** است؛ اجازهٔ مرورگر فقط با کلیک کاربر درخواست می‌شود. انتخاب مربوط به همان حساب روی همان مرورگر است.

متن پیام تا ۱۸۰ کاراکتر Unicode خلاصه می‌شود. عکس، ویدئو و صوت به‌ترتیب با `Photo`، `Video` و `Voice message`، همراه کپشن در صورت وجود، مشخص می‌شوند. اعلان گروه نام گروه و فرستنده را دارد. هیچ URL رسانهٔ خصوصی، JWT یا شناسهٔ ذخیره‌سازی فایل به Firebase فرستاده نمی‌شود؛ پیش‌نمایش متن/کپشن به سرویس Push فرستاده می‌شود و ممکن است روی صفحهٔ قفل نمایش داده شود. عکس و ویدئو در اعلان دانلود یا پخش نمی‌شوند.

## محیط

`frontend/.env.local` برای توسعه و build محلی، و `frontend/.env.production.local` برای مقادیر عمومی Firebase در build production تنظیم شده‌اند. این فایل‌ها ignored هستند. متغیرهای نمونه در `frontend/.env.example` قرار دارند:

```dotenv
VITE_FIREBASE_API_KEY=
VITE_FIREBASE_AUTH_DOMAIN=
VITE_FIREBASE_PROJECT_ID=
VITE_FIREBASE_STORAGE_BUCKET=
VITE_FIREBASE_MESSAGING_SENDER_ID=
VITE_FIREBASE_APP_ID=
VITE_FIREBASE_MEASUREMENT_ID=
VITE_FIREBASE_VAPID_KEY=
```

`VITE_FIREBASE_VAPID_KEY` همان Public key قسمت Project settings → Cloud Messaging → Web Push certificates است. Measurement ID فقط برای تطبیق با تنظیمات داده‌شده نگهداری می‌شود؛ Analytics بارگذاری نمی‌شود. همهٔ `VITE_*` عمومی‌اند. تغییرشان به build دوباره نیاز دارد. نشانی‌های API/socket محیط production باید متناسب با دامنهٔ واقعی استقرار تنظیم شوند؛ در این تغییر دامنهٔ production یا استقرار خارجی تعریف نشده است.

بکند هم در اجرای توسعه و هم `start:prod`، `backend/.env` را می‌خواند. کلیدهای واقعی فقط آنجا ذخیره شده‌اند؛ فایل ignored و با مجوز 0600 است. نمونهٔ بدون secret در `backend/.env.notifications.example` قرار دارد:

```dotenv
FIREBASE_NOTIFICATIONS_ENABLED=true
FIREBASE_PROJECT_ID=batgram-notification
# یکی از دو روش:
FIREBASE_SERVICE_ACCOUNT_PATH=/absolute/private/path/service-account.json
# یا هردو مقدار زیر؛ private key می‌تواند دارای \n باشد:
FIREBASE_CLIENT_EMAIL=
FIREBASE_PRIVATE_KEY=
```

در استقرار واقعی، مسیر JSON را بیرون از web root نگه دارید یا از secret manager محیط استفاده کنید. کلید خصوصی هرگز نباید در فایل عمومی، متغیر Vite، سورس یا commit قرار گیرد. Firebase CLI، Hosting، `firebase init` و `firebase deploy` برای این معماری لازم نیستند؛ فرانت روی میزبان موجود و ارسال روی NestJS انجام می‌شود.

### محیط توسعهٔ WSL با شبکهٔ Windows

در عیب‌یابی واقعی مشخص شد این دستگاه از Windows به OAuth و FCM دسترسی دارد، ولی اتصال TLS از WSL timeout می‌شود. کلید سرویس‌اکانت با گوگل احراز هویت شد و FCM درخواست واقعیِ توکن مرورگر ثبت‌شده را پذیرفت. برای همین محیط محلی این مقادیر در `backend/.env` فعال شده‌اند:

```dotenv
FIREBASE_TRANSPORT=windows
FIREBASE_WINDOWS_NODE_PATH="/mnt/c/Program Files/nodejs/node.exe"
```

این حالت فقط ارسال Firebase را با Admin SDK موجود، در یک پردازش کوتاه‌عمر Windows Node انجام می‌دهد. هیچ پروکسی، listener یا پورت جدیدی ایجاد نمی‌کند. credential و پیام از stdin پردازش محلی عبور می‌کنند؛ در آرگومان فرمان یا فایل موقت ذخیره نمی‌شوند. پردازش Windows حداکثر ۶٫۵ ثانیه و والد حداکثر ۷ ثانیه منتظر می‌مانند؛ سقف هم‌زمانی و جدابودن تأیید پیام چت نیز حفظ می‌شود. نبود Windows Node یا قطع شبکه فقط Push را ناموفق می‌کند. لاگ موفقیت `Firebase accepted N notification(s)` به معنی پذیرفته‌شدن درخواست توسط FCM است؛ نمایش روی دستگاه همچنان به مجوز، وضعیت صفحه و سیستم‌عامل وابسته است.

برای production روی سرور Linux دارای دسترسی گوگل، `FIREBASE_TRANSPORT=direct` بگذارید یا این متغیر را حذف کنید؛ `direct` پیش‌فرض کد است. مسیر Windows ویژهٔ توسعهٔ WSL است و نباید به env سرور Linux منتقل شود.

خطای `EADDRINUSE :::3333` در عیب‌یابی از نسخهٔ آزمایشی بکند بود که روشن مانده بود. آن پردازش متوقف شد. فقط یک نمونهٔ بکند روی پورت 3333 اجرا شود؛ نمونهٔ دوم را برای تست هم‌زمان روی همین پورت اجرا نکنید.

Firebase Cloud Messaging API و FCM Registration API پروژه باید فعال باشند. مرورگر به HTTPS یا localhost، Service Worker، Push API و مجوز اعلان نیاز دارد. iOS نیازمند نسخهٔ پشتیبان Web Push و نصب در Home Screen است. بسته‌بودن کامل مرورگر یا محدودیت سیستم‌عامل می‌تواند تحویل را متوقف یا عقب بیندازد.

## سرویس‌ورکر و حریم حساب

همان سرویس‌ورکر ریشهٔ `/sw.js` هم PWA و هم Push را اجرا می‌کند؛ worker موازی با scope مشابه ساخته نمی‌شود. build با esbuild کد Push را به‌صورت محلی bundle و به worker موجود اضافه می‌کند. هیچ `importScripts` یا اسکریپت Google CDN هنگام نصب worker وجود ندارد. در توسعه، Vite همین `/sw.js` را فقط با handler اعلان و بدون کش فایل‌های برنامه سرو می‌کند؛ در production رفتار کش عمومی و صفحهٔ offline قبلی حفظ شده است.

ثبت مرورگر و گرفتن توکن با Firebase SDK فرانت انجام می‌شود. بکند با Admin SDK فقط **data-only** می‌فرستد؛ handler استاندارد `push` در worker دادهٔ FCM را می‌خواند و تنها محل تصمیم برای نمایش اعلان سیستم است. این کار جلوی اعلان خودکار تکراری و بلعیده‌شدن Push توسط یک صفحهٔ عمومیِ visible را می‌گیرد. worker قبل از نمایش از پنجره‌های داشبورد با MessageChannel وضعیت جاری حساب/چت/focus را می‌پرسد؛ پاسخ‌ندادن صفحات عمومی مانع نمایش اعلان نیست. دریافت دوبارهٔ یک messageId به همان حساب در پنج دقیقه حذف می‌شود. پیام‌های قدیمی‌تر از پنج دقیقه و payload نامعتبر نمایش داده نمی‌شوند. tag ثابت هر گفتگو اجازه می‌دهد اعلان مرورگر با پیام جدید همان گفتگو جایگزین شود.

حساب متصل به مرورگر و انتخاب Push در IndexedDB worker ثبت می‌شوند تا بعد از بستن همهٔ تب‌ها باقی بمانند. خروج، غیرفعال‌کردن Push و تغییر حساب، binding و اعلان‌های نمایش‌داده‌شده را پاک/به‌روز می‌کنند؛ unregister سمت API به مالک حساب محدود است. حتی اگر API موقع خروج در دسترس نباشد، binding محلی دریافت اعلان حساب قبلی را متوقف می‌کند. کلیک اعلان تنها شناسهٔ عددی گفتگو را می‌پذیرد؛ پنجرهٔ موجود را focus و navigate می‌کند یا لینک داخلی `/dashboard/websocket/:chatId` را باز می‌کند. اعتبارسنجی نشست و عضویت API تغییری نکرده‌اند.

توکن هر نصب در `PushSubscription` ذخیره می‌شود؛ ثبت دوباره، rotation و جابه‌جایی حساب را پوشش می‌دهد. توکن‌های نامعتبر FCM پاک می‌شوند؛ توکن‌های بدون تمدید بیش از ۹۰ روز از ارسال کنار گذاشته می‌شوند. فرانت هنگام اتصال، بازگشت اینترنت و هر ساعت توکن را تازه/ثبت می‌کند.

## قطع دسترسی Firebase

- هیچ درخواست Google بخشی از راه‌اندازی، ورود، محافظ مسیر، دریافت تاریخچه یا ارسال پیام نیست.
- SDK فرانت فقط برای مرورگر دارای opt-in به‌صورت lazy بارگذاری می‌شود. اتصال حداکثر ده ثانیه منتظر می‌ماند و خطا فقط در تنظیمات اعلان نمایش داده می‌شود؛ UI اصلی و اعلان سوکتی ادامه دارند.
- نبود یا خرابی credential بکند مانع شروع Nest نمی‌شود؛ فقط Push خارجی غیرفعال می‌شود.
- dispatch بعد از commit و بدون await در مسیر تأیید ارسال است. شکست اعلان پیام ذخیره‌شده را ناموفق اعلام نمی‌کند.
- ارسال خارجی سقف هشت ثانیه، وقفهٔ ۶۰ثانیه‌ای پس از شکست، و حداکثر چهار درخواست واقعی هم‌زمان دارد. روی اتصال قطع‌شده retry خودکار پیام چت انجام نمی‌شود.

Push بهترین‌تلاش است؛ برای پیام‌رسانی آفلاین outbox پایدار اضافه نشده است. مبدأ داده و unread همچنان دیتابیس چت است. پس از اتصال مجدد تاریخچه و فهرست گفتگوها تازه می‌شوند.

## migration و بررسی

```bash
cd backend
npx prisma migrate deploy
npx prisma generate
npm run build
npm test -- --runInBand
npm run test:notifications:integration

cd ../frontend
npm run build
npm run lint
npm test
npm run test:pwa
```

migration `20261104160000_notifications` روی دیتابیس محلی اعمال شده است. تست یکپارچه از PostgreSQL، HTTP و Socket.IO واقعی با حساب‌های موقت استفاده می‌کند و تنها transport گوگل را جایگزین می‌کند. هر سه حالت، چند تب، چت گروهی/دونفره، رسانه/کپشن، مالکیت توکن و مستقل‌بودن ارسال REST از شکست Push بررسی می‌شوند.

در بررسی این تغییر: ۸۹ تست فرانت، ۴۰ تست بکند، ۴ تست یکپارچهٔ اعلان، ۳ تست PWA، build دو طرف و lint فایل‌های مرتبط موفق بودند. تست رسانهٔ قدیمی برای dependency تماس یک mock ناقص داشت؛ fixture آن کامل شد.

Chrome واقعی با حساب‌های آزمایشی ایزوله، اعلان سوکتی و بازکردن گفتگو، سکوت چت باز، هر دو تم، نمایش موبایل، خروج هم‌زمان تب‌ها و عدم خرابی برنامه با مسدودکردن Google را تأیید کرد. تزریق payload با قالب FCM از پروتکل تست Chrome، با بسته‌بودن صفحهٔ اپ، به ثبت اعلان واقعی توسط worker منجر شد. این تست تحویل از شبکهٔ Firebase نیست. در تست اولیه اتصال مستقیم WSL به OAuth گوگل timeout شد. در عیب‌یابی بعدی احراز هویت واقعی سرویس‌اکانت و پذیرش ارسال واقعی به توکن ثبت‌شده، هم از Windows و هم با transport جدید بکند WSL تأیید شدند. نمایش نهایی روی مرورگر شخصی کاربر نیازمند تأیید او است. کلیک اعلان سیستم و نصب روی iOS نیز نیازمند بررسی روی دستگاه مقصد هستند.

منابع: [شروع FCM وب](https://firebase.google.com/docs/cloud-messaging/web/get-started)، [دریافت پیام](https://firebase.google.com/docs/cloud-messaging/web/receive-messages)، [Admin SDK](https://firebase.google.com/docs/admin/setup).
